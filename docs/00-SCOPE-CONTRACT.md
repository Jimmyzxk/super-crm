## 0. 这份文档是什么

这是整个项目的**根文档**。所有其他文档、所有代码、所有排期都从属于它。

它回答三个问题：

1. 我们在做什么（一句话）
2. V1 做什么、不做什么（清单）
3. **想加东西时，凭什么才能加**（准入规则）

**第 3 条是本文档存在的主要理由。** 功能清单谁都会写，拦住范围膨胀才是难的。

---

## 1. 一句话定义

> 一个以线索池、客户池、商机池为事实基础，把优秀销售的推进方法沉淀下来，并在每一笔业务中给出可执行建议的 AI CRM。

**不是**：营销自动化平台、数据中台、全功能 CRM，也不是脱离业务事实自由聊天的 AI 助手。
AI 销售教练是核心：卸载后，系统只剩记录工具，无法完成“发现问题、建议动作、复用赢单方法”的闭环。

## 2. 唯一成功标准

**分两级，不可混淆。**

### 2.1 内部试跑（不是成功标准）

> 自己连续使用 5 个工作日。

**它只证明一件事：流程能跑通，没有硬伤。**

它**不能**证明"销售愿意用"——你知道每个按钮为什么在那里，你不会因为看不懂而放弃。
自己用得顺手，和一个没参与设计的人用得顺手，是两回事。

### 2.2 V1 成功（唯一标准）

> **至少 1 名非开发者的真实销售，在完整 V1 价值链路可用后连续使用 5 个工作日，第 5 天仍在用，并实际完成过线索、客户、商机、通知和建议相关动作。**

"非开发者"、"连续 5 天"和"实际使用完整价值链路"是硬条件。人数可以少（1 个就够），但不能是自己。

不达标 = V1 没做完，无论功能多齐。
达标 = V1 做完了，无论功能多少。

> **为什么必须卡死这一条**：上一个项目做了 444 个源文件、605 个测试，**零真实用户**。
> 它一直"感觉快好了"，因为验证者始终是开发者自己。
> 留任何"自己用也算"的口子，这个失败模式就会原样重演。

### 2.3 两个验证门，不得混淆

| 门 | 证明什么 | 不能证明什么 |
|---|---|---|
| 线索工作台门（阶段 3.5） | 真实销售能录入、跟进、完成任务并收到提醒 | 客户池、商机池、AI 教练和销冠打法有价值 |
| 完整 V1 价值门（阶段 6） | 三池事实、通知、质检建议、赢单复盘和打法推荐能被真实销售连续使用 | 因果提升或适用于所有销售团队 |

阶段 3.5 通过，只允许进入后续开发；不能据此宣布 V1 成功或“复制销冠”已经成立。

### 2.4 不作为成功标准

写在这里防止自我安慰：

- ❌ 功能数量
- ❌ 测试覆盖率
- ❌ 代码行数
- ❌ 架构优雅程度
- ❌ 演示效果好
- ❌ **自己觉得好用**

## 3. V1 全部内容：销售智能闭环

**V1 只做下面这条池化闭环。每一步都必须能在角色工作视图中完成，不需要跨页面寻找数据。**

```
1. 进入线索池    →  手工 / CSV / 表单 / 外部 API，统一去重、来源证据和自动评分
2. 角色化工作    →  销售、主管、管理员从同一池读取不同范围和聚合，不复制数据
3. 判断先跟谁    →  数据质量 + 意向质量 + 时效风险，给出可解释优先级
4. 推进并留痕    →  30 秒内记录事实、客户异议、下一步和承诺时间
5. 转化经营      →  线索转客户并创建商机，保留不可变的来源与转化关系
6. 自动质检建议  →  对照阶段要求和已审核打法，指出缺口并建议下一动作
7. 赢单复盘复用  →  从真实时间线提炼节奏，经主管审核后反哺商机池
```

**第 4、6、7 步是产品差异化，不能再以“后续 AI 能力”为理由省略。**
只实现 CRM 对象联动，只能证明数据能流转，不能证明系统能复制销冠方法。

## 4. V1 明确不做

以下每一条都是**已知会被想起来、且必须拒绝**的东西。

### 4.1 不做的功能

- 营销活动、渠道管理、归因分析
- 复杂公海规则、自动划转、抢单
- 完整业绩管理、提成计算
- 自动化营销、批量触达、AI 外呼
- 复杂预测和自由分析（允许池列表所需的基础聚合与固定口径报表）
- SDR 交接流程
- 复杂表单编辑器（条件跳转、多主题、抽奖、短链）
- 工作流引擎、自定义字段、自定义对象
- 自定义角色、权限矩阵配置、部门树
- 合同、订单、发票、库存、售后
- 四层身份归一、自动合并、合并冲突队列
- 自动分配规则

### 4.2 不做的技术投入

- 复杂 CQRS、多套 projection 读模型、事件溯源（允许为在线池列表服务的轻量当前状态快照、固定口径增量汇总和达到容量门槛后的时间分区）
- 消息队列（BullMQ / Redis 队列）
- 微服务拆分
- GraphQL / tRPC
- 状态管理库
- 重型组件库
- 对象存储 / 文件上传
- 多语言 / 国际化
- 移动 App（响应式 Web 即可）
- 监控 / APM 平台

### 4.3 不做的插件能力

- 插件热加载 / 运行时安装
- 插件商店 / 市场
- 第三方开发者文档 / SDK
- 插件沙箱 / 权限隔离
- 插件版本兼容层
- 插件间依赖管理

### 4.4 关于表单

V1 表单插件只做**最小获客表单**：单行文本、手机号、邮箱、公司、单选、多选、下拉、隐私同意（8 种）。

**明确不做**：条件显示、跳题、主题市场、资产库、欢迎页/成功页定制、倒计时、二维码、抽奖、短链。

> 上一个项目的文档也写了"不做条件跳转"，然后做了。
> **这次如果要做，必须走第 6 节。**

## 5. 核心与插件的边界

### 5.1 判定规则

> **卸载它，系统还能用吗？**
> - 不能用 → 核心
> - 能用 → 插件

### 5.2 核心（永不插件化）

```
身份与权限   用户、角色、权限范围、审计、多租户隔离
CRM 六对象   客户 / 联系人 / 线索 / 跟进 / 商机 / 任务
销售闭环     评分、优先级、通知、基础报表
```

### 5.3 插件（客户差异处）

短信/邮件/企微、外部 CRM 双向同步、高级营销归因、高级报表。

外部 API 进线和 AI 销售教练属于核心：前者保证线索不被入口限制，后者保证系统不是被动记录器。

### 5.4 V1 的插件策略

> **V1 只做插件"接口"，不做插件"市场"。**

- V1 暴露 `ctx.core.createLead` + 3 个实际使用的 UI 挂载点；**不实现事件总线**
- **V1 自己实现 1 个插件（表单获客）作为参照实现**，验证接口够不够用
- 接口不够用的地方记进 [13](./13-PLUGIN-CONTRACT.md) 第 8 节

**插件接口的正确性只能由真实插件验证。** 做一个自己要用的插件，比设计十个假想接口有用。

## 6. 准入规则（本文档的核心）

**任何不在第 3 节的东西，想进 V1，必须同时满足以下全部三条：**

### 条件 A — 闭环阻断

> 不做这个，销售智能闭环会**断掉**吗？

不是"体验更好"、不是"以后要用"、不是"顺手做了"。是**断掉**。

### 条件 B — 真实用户提出

> 是**真实销售在使用中**提出来的吗？

自己想到的不算。演示时觉得需要的不算。客户销售说"这个没有我没法用"才算。

**V1 试用开始前，这一条自动不满足。** 也就是说：**试用开始前，任何新增功能都不许进。**

### 条件 C — 有明确的完成定义

> 能用一句话说清"什么算做完"吗？

"优化用户体验"不算。"销售能在 30 秒内记完一笔跟进"算。

### 6.1 三条都满足时怎么做

1. 写进本文档第 3 节
2. **记录为什么**（哪个销售、什么场景、闭环怎么断的）
3. 从 V1 里砍掉等量的东西，或明确延期时间
4. 在第 8 节变更日志留痕

### 6.2 一个演练

假设有人提出"加个渠道归因功能"：

| 条件 | 判定 |
|---|---|
| A 闭环会断吗？ | ❌ 没有归因，销售照样能跟线索 |
| B 真实用户提出？ | ❌ 试用还没开始 |
| C 完成定义清晰？ | ❌ "看到线索来自哪个渠道"——看到之后呢？ |

**三条全不满足 → 拒绝。**

## 7. 上一个项目的教训

同一个人，同样的目标，2026-07-10 到 2026-08-11，产出 **444 个源文件、605 个测试、83 个数据库迁移，零真实用户**。

失败的不是执行力，是范围控制。四条具体教训：

### 教训 1：文档写了"不做"，代码还是做了

7-10 的重构决策文档明确写着 V1 表单**不做条件跳转**。8-04 的进度记录里，条件显示和跳转已经实现。

**没人决定要做它，它就是被"顺手"做出来的。**

→ **对策**：第 6 节准入规则 + 第 8 节变更日志。改范围必须留痕。

### 教训 2：为想象中的未来建基础设施

建了两套 projection 读模型（归因 + 销售报表），深度可观，**对交付零价值**。

→ **对策**：第 4.2 节明确禁止此类投入。插件接口也按最小验证原则（5.4）。

### 教训 3：把"功能齐了"当成"做完了"

一个月内做完全部模块，但**评分不会自动跑、销售收不到通知**——闭环从未打通，也从未有人用过。

→ **对策**：第 2 节唯一成功标准。功能齐 ≠ 做完。

### 教训 4：验证欠账会滚雪球

3000+ 行代码从未跑过 typecheck。到发现时，问题已多到无法定位。
444 个源文件从未进版本控制，没有任何回滚点。

→ **对策**：[17](./17-DELIVERY-PLAN.md) 每阶段三重验证 + 立即提交。
