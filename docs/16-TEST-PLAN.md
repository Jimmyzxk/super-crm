## 1. 测试哲学

### 1.1 不追求覆盖率

上一个项目有 **605 个测试全绿，零真实用户**。测试数量不是质量指标。

### 1.2 唯一标准

> **每个测试必须能说清"它防止了什么真实故障"。**

说不清的测试删掉。

### 1.3 反面例子

| 测试 | 防止什么 | 判定 |
|---|---|---|
| "createLead 返回的对象有 id 字段" | 无 | ❌ 删 |
| "组件能正常挂载" | 无 | ❌ 删 |
| "跨租户查不到别人的线索" | 数据泄露 | ✅ 留 |
| "从 DISCOVERY 跳到 NEGOTIATION 被拒绝" | 阶段数据失真 | ✅ 留 |
| "线索创建后自动有分数" | 闭环第 2 步失效 | ✅ 留 |

| 类型 | 覆盖 | 数量要求 |

## 3. 租户隔离测试（最高优先级）

### 3.1 为什么最高

目标用户是对外卖 SaaS。**一次跨租户泄露 = 产品死亡。**

而 RLS 有一个致命特性：**配错时是静默失效的**——查询照常返回结果，只是返回了不该看到的数据。没有测试就发现不了。

### 3.2 测试范式（每张表照抄）

```ts
describe('租户隔离：leads', () => {
  it('租户 A 查不到租户 B 的线索', async () => {
    const { tenantA, tenantB } = await seedTwoTenants()
    const leadB = await createLeadIn(tenantB, { contactName: '租户B的线索' })

    // 用租户 A 的上下文查询
    const result = await withTenant(ctxOf(tenantA), (tx) =>
      tx.select().from(leads).where(eq(leads.id, leadB.id))
    )

    expect(result).toHaveLength(0)   // 必须查不到
  })

  it('租户 A 无法更新租户 B 的线索', async () => { /* ... */ })
  it('租户 A 无法删除租户 B 的线索', async () => { /* ... */ })
})
```

| `users` | ☐ |
| `leads` | ☐ |
| `customers` | ☐ |
| `contacts` | ☐ |
| `activities` | ☐ |
| `tasks` | ☐ |
| `opportunities` | ☐ |
| `opportunity_stage_history` | ☐ |

**新建表时必须同时加这条测试，否则不允许合并。**

### 3.4 额外的隔离测试

| 场景 | 断言 |
|---|---|
| `withTenant` 传空 tenantId | 抛错，不执行查询 |
| 应用连接角色 | 确认不是表 owner（否则 RLS 失效） |
| 未设 `app.tenant_id` 时查询 | 返回 0 行（不是全部行） |
| 插件自有表事务 | 必须在当前租户上下文内查询；跨租户查询返回空，核心表写入只能经 `ctx.core.createLead` |
| `withoutTenant` 调用点 | 全仓库只有 2 处，且都是读 `tenants`（login 校验租户状态 / cron 遍历租户） |
| `auth_lookup_user` 调用点 | 全仓库只有 1 处（`login`） |

### 3.5 跨租户设计约束的回归测试

以下九条是文档评审时发现的**真实设计矛盾**，已修正。每条必须有测试守着，防止实现时踩回去：

| # | 约束 | 测试断言 |
|---|---|---|
| 1 | 邮箱规范化后全局唯一 | 建 `Alice@X.com` 最终存 `alice@x.com`；再建 ` alice@x.com ` 失败；两种写法登录都成功 |
| 2 | cron 逐租户扫描 | 造 2 个租户各 1 条超时任务 → 跑一次 cron → **两个租户都收到通知**（证明没有因 RLS 漏扫） |
| 3 | 任务可挂客户 | 在客户上记跟进并设下次时间 → 任务创建成功且 `customer_id` 非空 |
| 4 | 未分配线索不建任务 | 表单提交创建线索 → **无 OPEN 任务**；分配后 → 任务出现且 `due_at = 分配时间+24h` |
| 5 | 插件通过白名单建线索 | 插件调 `ctx.core.createLead` 成功；插件直接写 `leads` 表被阻止 |
| 6 | **登录能窄范围绕过 RLS** | 函数属主 `rolcanlogin = false AND rolbypassrls = true`；应用角色不是其成员；`auth_lookup_user('x@y.com')` 返回记录；同一应用连接裸查 `users` 返回 0 行 |
| 7 | **会话版本失效且查询带租户** | 登录拿 token → 停用用户 → 旧 token 请求为 401；伪造/篡改 tenantId 的 token 验签失败；合法签名但 tenantId 与用户不匹配时也为 401 |
| 8 | 手工重复线索两阶段确认 | 首次命中返回 `created:false` 且数据库零写入；确认后只创建 1 条；选择查看则不创建 |
| 9 | 表单提交原子关联 | 两条并发提交各自关联正确；任一步抛错后 submission / Lead / link 均不落库；公开定位函数只返回已发布表单的 tenantId |

> **第 2 条**：RLS 配错时是静默失效的。cron 若忘了逐租户循环而直接全表扫，
> 结果是**一条通知都不生成**（返回 0 行），而不是报错。没有这条测试，会以为"没有超时任务"。

> **第 6 条**：`withoutTenant()` 不绕过 RLS；同时 `FORCE ROW LEVEL SECURITY` 会约束普通表属主。
> 因此必须同时验证专用函数属主确有 `BYPASSRLS`、函数能查到、应用连接裸查查不到、应用角色不能切换到函数属主，缺一都说明实现走偏。

> **第 7 条**：JWT 是无状态的，签发后在有效期内一直有效。
> 不做 `session_version` 比对，"停用用户后现有会话立即失效"就是一句空话。

## 4. 业务规则测试

### 4.1 线索状态机（[03](./03-FEATURE-LEAD.md) 6.2）

**合法转换**（每条一个测试）：

| 从 | 到 | 触发 |
|---|---|---|
| NEW | CONTACTED | 首次记跟进（自动） |
| CONTACTED | QUALIFIED | 手动，需填需求说明 |
| QUALIFIED | CONVERTED | 转客户 |
| 任意非终态 | DISCARDED | 手动，需填原因 |
| DISCARDED | NEW | MANAGER 恢复 |

**必须被拒绝**：

| 场景 | 期望 |
|---|---|
| NEW → QUALIFIED（跳过 CONTACTED） | `INVALID_TRANSITION` |
| NEW → CONVERTED | `INVALID_TRANSITION` |
| CONTACTED → CONVERTED | `INVALID_TRANSITION` |
| CONVERTED → 任意 | `INVALID_TRANSITION` |
| 放弃时不填原因 | `VALIDATION_ERROR` |
| 放弃原因选 OTHER 但不填说明 | `VALIDATION_ERROR` |

### 4.2 商机阶段机（[07](./07-FEATURE-OPPORTUNITY.md) 4.2）

**合法**：相邻推进、相邻回退（需填原因）、非终态→LOST、NEGOTIATION→WON

**必须被拒绝**：

| 场景 | 期望 |
|---|---|
| DISCOVERY → NEGOTIATION（跳级） | `INVALID_TRANSITION` |
| DISCOVERY → WON（早期直接赢单） | `INVALID_TRANSITION` |
| PROPOSAL → WON | `INVALID_TRANSITION` |
| WON → 任意 | `INVALID_TRANSITION` |
| LOST → 任意 | `INVALID_TRANSITION` |
| 丢单不填原因 | `VALIDATION_ERROR` |
| 回退不填原因 | `VALIDATION_ERROR` |

### 4.3 评分规则（[05](./05-FEATURE-SCORING.md)）

**每个 operator 一个测试**：`EXISTS` `NOT_EXISTS` `EQUALS` `CONTAINS` `STARTS_WITH` `GT` `GTE` `IN`

**计算逻辑**：

| 场景 | 期望 |
|---|---|
| 多规则命中 | 分数 = 权重之和 |
| 权重和 > 100 | 截断为 100 |
| 权重和 < 0 | 为 0（不允许负分） |
| 无规则命中 | 0 分，理由"暂无加分项" |
| 从未评分 | `score = null`，与 0 分可区分 |
| 理由拼接 | 按 `sort_order` 升序 |
| 理由超 500 字 | 截断到最后一个完整规则 + "等" |
| 规则全部停用 | 所有线索 0 分 |

**自动触发（重点，上个项目断在这）**：

| 触发点 | 断言 |
|---|---|
| 创建线索后 | **不做任何操作，score 非 null** |
| 补充 company_name 后 | 分数增加 |
| 记一条 INTERESTED 跟进后 | 分数增加 |
| 记一条 REFUSED 跟进后 | **分数下降**（负权重生效） |
| 评分抛错时 | 线索仍创建成功，score = null |

### 4.4 超时判定（[04](./04-FEATURE-FOLLOWUP.md) 4.4）

| 场景 | 期望 |
|---|---|
| `due_at` < now 且 OPEN | 判定为超时 |
| `due_at` < now 但 DONE | 不算超时 |
| `due_at` 在 2 小时内 | 判定为临近 |
| `due_at` 在 3 小时后 | 正常 |

### 4.5 工作台排序（[04](./04-FEATURE-FOLLOWUP.md) 5.3）

| 场景 | 期望 |
|---|---|
| 超时 vs 今天到期 | 超时在前 |
| 两条都超时 | 超时久的在前 |
| 高分未跟进 vs 普通 | 高分在前 |
| 四档混合 | 严格按档位顺序 |

### 4.6 权限矩阵（[09](./09-FEATURE-ADMIN.md) 2.4）

**矩阵每一格都要测。** 重点：

| 场景 | 期望 |
|---|---|
| SALES 查看别人的线索 | `NOT_FOUND` |
| SALES 分配线索 | `FORBIDDEN` |
| SALES 访问设置页 | 导航不渲染 + Action 返回 `FORBIDDEN` |
| SALES 直接调用 `createUser` | `FORBIDDEN`（绕过 UI 也拦住） |
| MANAGER 改评分规则 | `FORBIDDEN` |
| ADMIN 手工建线索未指定负责人或指定 ADMIN | `VALIDATION_ERROR`；指定 active SALES/MANAGER 才成功 |
| 停用最后一个 ADMIN | `INVALID_TRANSITION` |
| 修改自己的角色 | `INVALID_TRANSITION` |

### 4.7 去重（[03](./03-FEATURE-LEAD.md) 4）

| 场景 | 期望 |
|---|---|
| 手工录入重复手机号（未确认） | 返回 `created: false` + `duplicateOf`，线索/任务/审计均无新增 |
| 手工录入重复手机号（确认） | 第二次带 `confirmDuplicate: true`，仅创建 1 条新线索 |
| 表单提交重复手机号 | 创建成功 + `is_possible_duplicate = true` |
| 查重忽略 DISCARDED | 已放弃的不算重复 |
| 联系人手机号租户内重复 | `DUPLICATE_PHONE` |
| 不同租户相同手机号 | 都能创建（隔离） |

### 4.8 通知去重（[08](./08-FEATURE-NOTIFICATION.md) 5.1）

| 场景 | 期望 |
|---|---|
| 同一任务扫描两次 | 只生成 1 条 `TASK_OVERDUE` |
| 先 DUE_SOON 后 OVERDUE | 生成 2 条（不同 type） |
| 定时任务并发执行 | 不重复生成 |

### 4.9 主联系人唯一（[06](./06-FEATURE-CUSTOMER.md) 5.2）

| 场景 | 期望 |
|---|---|
| 设置新主联系人 | 原主自动降级，同事务 |
| 删除主联系人 | `INVALID_TRANSITION` |
| 删除唯一联系人 | `INVALID_TRANSITION` |
| 数据库层 | 部分唯一索引阻止两个主联系人 |

### 4.10 业务池与角色视图

每个池至少覆盖：

- 同一对象以 SALES / MANAGER / ADMIN 查询时 ID、状态和跨池关系一致；
- SALES 只能看到自己负责的数据，MANAGER 看到团队范围，ADMIN 看到租户范围；
- 角色参数不能由客户端伪造，服务端只信会话；
- 主管指标点击后进入带等价筛选的业务池，列表对象与指标口径一致；
- 游标分页无重复、无遗漏，排序字段相同以 ID 稳定分界；
- 列表查询计划不出现历史表无界扫描、深 OFFSET 或 N+1；
- `lead_conversions` 创建后不可更新；跨租户关系被外键和 RLS 双重拒绝；同租户但商机属于其他客户时也被复合外键/延迟约束拒绝。

## 5. 闭环端到端测试

### 5.1 主链路（必须有）

```
① 创建线索（手工）
② 断言：自动有分数和理由
③ 断言：自动创建 FIRST_RESPONSE 任务
④ 打开工作台，断言这条排在队列里
⑤ 记一条跟进
⑥ 断言：状态 NEW → CONTACTED
⑥a 断言：状态记录新增 NEW → CONTACTED，包含操作者与时间
⑦ 断言：任务被完成
⑧ 断言：分数重算
⑨ 填了下次跟进时间 → 断言新任务创建
⑩ 把 due_at 改到过去，跑扫描任务
⑪ 断言：生成超时通知
⑫ 断言：铃铛未读数 = 1
```

**这条链路只覆盖基础执行闭环。它通过不代表智能闭环已通，还必须通过 5.4。**

### 5.2 转化链路

```
线索 → 标记已确认需求 → 转客户并原子创建本次转化商机（查重）→ 推进阶段 → 赢单
```

断言每一步的状态变化和任务生成/取消，并至少覆盖：

- `CONTACTED` 和未分配线索转化均被拒绝且零写入
- 无重复时一次生成客户、主联系人、`CONVERTED` 状态历史、转化商机、`null → DISCOVERY` 历史及唯一 OPEN 阶段任务
- 手机号命中时只能关联已有客户或修改手机号；相同手机号强建返回 `DUPLICATE_PHONE`
- SALES 不得关联其他销售的客户；MANAGER / ADMIN 可在当前租户处理，跨租户 ID 一律不可见
- 同租户内故意错配 customer 与 opportunity 时提交失败；客户来源线索和商机来源线索只能从 `lead_conversions` 读取，不存在重复来源字段
- 旧数据回填只能从唯一的状态历史/审计证据取得操作人和转化时间；缺失或冲突时进入隔离清单，不使用迁移执行人或当前时间伪造
- 在事务的每个写入点注入失败，断言客户、联系人、线索、商机、历史、任务和审计全部回滚
- 两个并发转化只有一个成功，不产生重复客户或转化商机
- 两个并发阶段推进只有一个成功，失败方不写历史、任务或审计
- 客户经营状态随多笔商机聚合变化，不存在可直接写入的客户阶段
- 商机普通跟进不设下次时间时保留 `STAGE_PUSH`；设下次时间时切换为 `FOLLOW_UP`；完成该 `FOLLOW_UP` 后按原 `stage_entered_at + SLA` 恢复 `STAGE_PUSH`

### 5.3 插件链路

```
启用表单插件 → 建表单 → 发布 → 模拟提交 → 断言线索创建
停用插件 → 断言导航消失、闭环仍可走通
```

### 5.4 智能闭环

```
API 创建线索 → 自动质量判断 → 跟进未设下一步 → 生成质检建议
→ 销售采纳并创建任务 → 推进并赢单 → 自动复盘
→ 第 3 个同类已审核样本后发布打法 → 新商机获得打法推荐并反馈
```

断言每条建议有事实证据、失败不回滚业务事实、少于 3 个样本不可发布、建议不自动修改阶段。

### 5.5 完整 V1 价值门

阶段 3.5 只验证线索工作台，不得作为完整 V1 成功证据。完整价值门必须在三池、通知、AI 质检和赢单打法链路都可用后执行：

```
同一销售在 5 个工作日内：
① 从线索池处理至少一条真实线索
② 在客户池查看同一对象的经营状态
③ 在商机池推进或记录一笔真实商机
④ 收到并处理一次通知
⑤ 采纳或明确忽略一次质检建议
⑥ 查看一次赢单复盘或打法推荐（没有本期赢单时只能使用历史真实且已审核的赢单样本）
```

至少记录：每天是否完成有效业务动作、首次操作耗时、有效跟进是否包含下一步、建议采纳/忽略原因、通知是否在页面可见。只完成被要求的点击，不算通过。

**失败门槛**：无法招募非开发者销售，或 5 天中少于 4 天完成有效业务动作，或第 5 天没有主动返回系统处理业务，则停止扩建并重新评估产品价值。通过阶段 3.5 不能替代此门。

## 6. 测试数据规范

### 6.1 禁止合成数据进入业务界面

> 上个项目的界面上出现了 `Synthetic Lead`、`Browser Anonymous`、公司名是裸 UUID（`Second 0a7e91bf-ccb9-...`）。
> **销售第一眼看到这些，对整个系统的信任就没了。**

**规则**：
- 测试数据只存在于测试数据库
- 演示数据用真实感的中文（`李明` / `星海智能科技`），不用 `Test User 1`
- 生产数据库禁止出现测试数据

### 6.2 测试隔离

- 每个测试文件用独立的租户
- 测试之间不共享状态
- 测试数据库与开发数据库分离（`TEST_DATABASE_URL`）
