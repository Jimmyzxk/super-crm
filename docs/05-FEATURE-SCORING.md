# 功能规格：智能评分

版本：v1.0 · 2026-08-11
从属于：[00-SCOPE-CONTRACT.md](./00-SCOPE-CONTRACT.md) · 场景依据：[02-USERS-AND-SCENARIOS.md](./02-USERS-AND-SCENARIOS.md)

---

## 1. 这个模块做什么

销售闭环的第 2 步：**告诉我先跟谁**。

给每条线索算一个 0-100 的分数，**并且说清楚为什么是这个分**。

---

## 2. 为什么评分在核心而不是插件

按 [00 范围契约](./00-SCOPE-CONTRACT.md) 5.1 的判定规则：

> 卸载它，系统还能用吗？

卸载评分 → 销售面对 50 条线索不知从何下手 → 凭感觉挑 → 闭环第 2 步断。

**所以评分是核心。**

---

## 3. 两条设计红线

### 红线 1：必须自动触发

> **上一个项目就断在这里。**
> 它建了评分规则表、规则引擎、配置界面、版本管理，全都做了——
> 但评分只能通过 `POST /leads/:id/score/recalculate` 手动触发，
> 没有任何自动调用点。结果新线索永远没有分数，"先跟谁"是假的。

**V1 要求**：线索创建、关键字段变更、跟进记录写入后，**自动重算，无需人工操作**。

### 红线 2：必须可解释

销售看到"85 分"而不知道为什么，只有两种反应：忽略它，或者不信任它。两种都等于评分没做。

**V1 要求**：每个分数都附带人话理由，例如：

> 72 分 · 填了公司名 +20，官网表单 +15，30 分钟内提交 +10，有职位信息 +5

## 4. 评分模型

### 4.1 计算公式

```
score = min(100, Σ 命中规则的 weight)
```

- 规则之间**独立叠加**，无优先级、无互斥
- 上限 100，超过截断
- 无规则命中 → score = 0（不是 null）
- 未评分过 → score = null（与 0 分区分）

> **为什么用简单叠加而不是加权模型**：可解释性优先。任何销售看一眼就能明白"填了公司名加 20 分"，而"逻辑回归权重 0.37"没人看得懂。

### 4.2 规则结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | |
| `tenant_id` | uuid | 租户独立配置 |
| `field` | text | 判定哪个字段 |
| `operator` | enum | 怎么判定 |
| `value` | text null | 比较值 |
| `weight` | int | 命中加多少分（-100 ~ 100） |
| `label` | text | **人话解释**，会显示给销售 |
| `enabled` | bool | 是否启用 |
| `sort_order` | int | 理由拼接顺序 |

### 4.3 可判定字段

V1 只开放这些字段，**不做任意字段判定**：

| field | 含义 |
|---|---|
| `company_name` | 公司名称 |
| `contact_email` | 邮箱 |
| `title` | 职位 |
| `source` | 来源标识 |
| `created_hour` | 创建时段（0-23） |
| `activity_count` | 跟进次数 |
| `last_activity_outcome` | 最近一次跟进结果 |

### 4.4 判定操作符

| operator | 语义 | value 示例 |
|---|---|---|
| `EXISTS` | 字段非空 | — |
| `NOT_EXISTS` | 字段为空 | — |
| `EQUALS` | 精确等于 | `form:abc123` |
| `CONTAINS` | 包含子串 | `有限公司` |
| `STARTS_WITH` | 前缀匹配 | `form:` |
| `GT` | 大于（数值） | `2` |
| `GTE` | 大于等于 | `1` |
| `IN` | 属于集合（逗号分隔） | `INTERESTED,CONNECTED` |

### 4.5 默认规则（新租户初始化时写入）

| label | field | operator | value | weight |
|---|---|---|---|---|
| 填了公司名 | `company_name` | EXISTS | — | 20 |
| 填了邮箱 | `contact_email` | EXISTS | — | 10 |
| 有职位信息 | `title` | EXISTS | — | 5 |
| 来自表单 | `source` | STARTS_WITH | `form:` | 15 |
| 已联系过 | `activity_count` | GTE | `1` | 10 |
| 明确有意向 | `last_activity_outcome` | EQUALS | `INTERESTED` | 25 |
| 明确拒绝 | `last_activity_outcome` | EQUALS | `REFUSED` | -40 |

**总分上限自然落在 85 左右**，给后续加规则留空间。

> 注意"明确拒绝 -40"：**负权重是必要的**。拒绝过的线索不应该因为公司名填得全就排在前面。

## 5. 自动触发时机

### 5.1 三个触发点

| 时机 | 触发条件 | 为什么 |
|---|---|---|
| **线索创建** | 手工录入 / CSV 导入 / 表单提交完成后 | 新线索必须立刻有分，否则工作台排不了序 |
| **关键字段变更** | `company_name`/`contact_email`/`title`/`source` 任一变更 | 补充信息后价值判断会变 |
| **跟进记录写入** | 每次 activity 写入后 | 有互动说明意向变化 |

### 5.2 实现方式：同步计算

**V1 用同步计算，不引入队列。**

理由：
- 规则数量在 10-30 条量级，全内存判定，实测毫秒级
- 引入队列意味着引入 Redis/BullMQ + worker + 失败重试 + 监控，是典型的"为想象中的规模建基础设施"
- 同步计算的失败可以立即反馈，异步的失败会静默

**性能兜底**：若单次评分超过 100ms，记警告日志。累积出现说明该考虑异步了——**那时再改，有数据支撑**。

### 5.3 失败处理

评分失败**不阻断主流程**。

例如创建线索时评分抛错：线索照常创建，`score = null`，记错误日志。

理由：线索进来是第一位的，评分是辅助。宁可没分，不可丢线索。

## 6. 理由生成

### 6.1 拼接规则

按 `sort_order` 升序，拼接所有命中规则：

```
{label} {+/-}{weight}，{label} {+/-}{weight}，...
```

示例：
```
填了公司名 +20，来自表单 +15，已联系过 +10
```

### 6.2 长度限制

理由字段上限 500 字符。超长时截断到最后一个完整规则，追加"等"。

### 6.3 无命中时

`score = 0`，理由 = `"暂无加分项"`。

**不显示空白**，销售要知道"是真的 0 分"而不是"没算"。

### 6.4 未评分时

`score = null`，UI 显示"还没有评分"。

## 7. 销售反馈

### 7.1 交互

评分旁边两个按钮：**准 / 不准**

点击后：
- 写入 `score_feedback` 表
- 按钮变为已选中态
- **不改变分数**

### 7.2 数据

| 字段 | 说明 |
|---|---|
| `lead_id` | 哪条线索 |
| `user_id` | 谁反馈的 |
| `score_at_feedback` | 反馈时的分数（快照） |
| `verdict` | `ACCURATE` / `INACCURATE` |
| `created_at` | |

**同一用户对同一线索的反馈可覆盖**（改主意了），保留最新一条。

### 7.3 V1 只收集，不自动调权重

**明确不做**：根据反馈自动调整规则权重。

理由：
- 样本量不足时自动调权重会震荡
- 自动调整后规则变得不可解释，违反红线 2
- 需要多少样本才够？不知道——**这正是要先收集数据的原因**

管理员可在设置页看到反馈统计（准 N 条 / 不准 M 条），据此手动调规则。

## 8. 规则配置

见 [09 设置与权限](./09-FEATURE-ADMIN.md) 第 4 节。

关键约束：
- 只有 ADMIN 能改
- 改完**立即生效**，但**不追溯重算历史线索**
- 每条规则必填 `label`（人话解释）

> **为什么不追溯重算**：单租户设计基线可达 500 万条线索，全量重算是重操作。且历史分数变化会让销售困惑。
>
> **V1 不提供「全量重算」按钮。** 它需要分批执行与断点续跑，而架构明确不引入队列——
> 写一个"异步执行"的按钮却没有任务模型，是开不出的支票。
>
> 现状可接受：线索只要有任何更新或跟进就会自动重算，历史数据会自然收敛。
> 真需要时走范围契约第 6 节，那时一并设计分批方案。

## 9. 边界情况

| 情况 | 处理 |
|---|---|
| 规则全部停用 | 所有线索 score = 0，理由"暂无加分项" |
| 权重之和为负 | score = 0（不允许负分） |
| 权重之和 > 100 | score = 100（截断） |
| `GT`/`GTE` 操作符用在非数值字段 | 规则保存时校验拒绝 |
| `IN` 的 value 为空 | 规则保存时校验拒绝 |
| 评分时线索已被删除 | 静默跳过，不报错 |
| 同一线索并发触发两次评分 | 后写入者生效（V1 不做锁） |
| 租户刚创建，没有规则 | 写入第 4.5 节默认规则 |

---

## 10. 明确不做

| 不做 | 理由 |
|---|---|
| 机器学习评分模型 | 无训练数据；且不可解释，违反红线 2 |
| 评分版本管理 | 上个项目做了，无人使用 |
| 评分历史曲线 | 销售不关心分数变化轨迹 |
| 分数区间自定义（A/B/C 级） | 数字已经够用 |
| 按规则组/优先级/互斥 | 增加复杂度，简单叠加够用 |
| 自动调权重 | 见 7.3 |
| 跨租户规则模板市场 | 超前 |

## 11. 验收清单

- [ ] **新建线索后，不做任何操作，它自动有分数和理由**
- [ ] 补充公司名后，分数自动增加
- [ ] 记一条"明确拒绝"的跟进后，分数自动下降
- [ ] 理由是人话，销售能看懂为什么是这个分
- [ ] 无命中时显示"暂无加分项"，不是空白
- [ ] 未评分显示"还没有评分"，与 0 分可区分
- [ ] 负权重生效：拒绝过的线索排在后面
- [ ] 分数上限 100，下限 0
- [ ] 「准/不准」按钮可点击，点击后状态保留
- [ ] 评分失败不阻断线索创建
- [ ] 单次评分耗时 < 100ms（超过则记警告）
- [ ] 改规则后新线索用新规则，历史线索分数不变
