## 1. 交付原则

### 1.1 每个阶段必须可用

阶段结束时，**系统能跑起来、能登录、能完成当前阶段的功能**。

不允许"这个阶段只写后端，下个阶段才能看到东西"。

### 1.2 每个阶段必须验证

```bash
pnpm typecheck && pnpm lint && pnpm test
pnpm dev    # 并在浏览器实际走一遍
```

**三个都绿 + 浏览器实际操作过，才算完成。**

> 上个项目有 3000+ 行代码从未跑过 typecheck，问题堆积到无法定位。

### 1.3 每个阶段必须提交

阶段完成即 `git commit`。不攒大提交。

### 1.4 先建池，再建角色视图

线索池、客户池、商机池先定义事实边界和查询契约；销售、主管、管理员视图随后从同一业务池生成。任何角色视图如果需要复制业务表、维护独立状态或扫描全量历史，阶段验收直接失败。

在阶段 0.5 通过前，暂停新增赢单复盘、团队打法和独立页面，先修正文档、表边界和列表查询。

### 阶段 0.5：池化数据契约、迁移 Spike 与容量基线（3-5 天）★ 新方向门禁

**产出**：三个业务池、公用过程数据、转化关系和角色视图的边界可以直接指导迁移和查询实现。

| 任务 | 完成标志 |
|---|---|

| 公共与独立数据清单 | 活动、任务、通知、建议、审计共享；阶段、评分、金额等池内独立 |

| `salescrm_migration` 权限边界 | 独立 `NOLOGIN BYPASSRLS` 角色持有回填函数；认证角色不复用，应用角色不能执行或 `SET ROLE` |
| 迁移 Spike | 在隔离数据库按 Expand → Backfill → Verify → Switch → Contract 跑通旧来源字段样本；覆盖已有客户关联、重复/并发、跨租户错配和坏数据隔离 |
| 迁移门禁 | Spike 不能证明旧关系可唯一映射、隔离清单可清零、或切换后无需长期双写时，冻结阶段 4 与 4.4，先修订契约和迁移方案 |

| 列表查询契约 | 游标分页、禁止历史全量 JOIN、禁止深 OFFSET 和无界 COUNT；固定数量超过 ceiling 时显示 `ceiling+` |
| 容量压测规格 | 定义单租户百万级数据分布、冷热比例、生成器接口和目标查询，不使用生产数据 |
| 容量静态门禁 | 池列表必须有 `tenant_id` 条件、`LIMIT + cursor`、排序字段加 `id`、有界摘要读取；禁止无界 `COUNT(*)`、深 `OFFSET`、列表历史全量 JOIN 和 N+1。代码审查或自动规则命中任一项即不准合并 |
| 查询基线契约 | 列出三个池的关键查询形状、目标 P95、候选索引和后续 1% / 100% `EXPLAIN (ANALYZE, BUFFERS)` 验证点 |

**验收**：表、关系、角色范围、查询形状、迁移 Spike 和压测口径通过评审，可以直接指导迁移与查询实现。阶段 0.5 不虚构尚未建表时的性能结果；实际执行计划在阶段 1、4 做 1% 验证，在阶段 4.4 做 100% 验证。任一门禁未通过，不以文档完成代替实现完成。

### 阶段 3.5：线索工作台可用性 Gate（5 个工作日）★ 关键节点

**这个阶段不写功能。**

到这里，线索工作台闭环可用：线索进来 → 自动评分排序 → 去跟 → 记一笔 → 超时提醒。
客户池、商机池、三池联动、销售教练与团队打法仍未完成，因此本阶段**只证明线索工作台是否值得继续做**，不证明完整 V1 价值、更不证明“复制销冠”成立。

> **为什么在这里试用，而不是等全做完**
>
> 上一个项目做了一个月、444 个源文件才想到要试用，结果闭环根本没通。
> **越早让真实销售碰到，返工越便宜。**
>
> 此时如果销售说"这东西不好用"，我们投入的仍是有限的线索工作台成本，改起来还来得及。
> 它不能替代完成三池、通知、教练与打法后的完整价值验证。

| 任务 | 说明 |
|---|---|
| 部署到可访问环境 | 试用者能打开 |
| 导入真实线索数据 | **不用合成数据** |
| 至少 1 名非开发者销售连续用 5 天 | 见本节通过标准；只验证线索工作台 |
| 每天收集反馈 | 记录：卡在哪、不会用什么、想要什么 |
| **不改功能** | 除非闭环断了（对照准入规则条件 A） |

**通过标准**：

| # | 检查 | 标准 |
|---|---|---|
| 1 | 第 5 天还在用吗 | 是 |
| 2 | 打开工作台到第一个动作 | ≤ 10 秒 |
| 3 | 记一条跟进 | ≤ 30 秒 |
| 4 | 超时后收到通知 | ≤ 5 分钟 |
| 5 | 有效业务操作 | 5 天中至少 4 天发生真实线索处理；第 5 天主动完成一次动作 |

**不通过怎么办**：

**停下来，不要进阶段 4。** 反馈指向哪里就修哪里——闭环不成立，做再多客户和商机也没用。

反馈中的新需求走准入规则第 6 节（**此时条件 B 已满足**，因为有真实销售在用了）。

| 公开提交接口 + 限流 | 同 IP 每分钟 10 次 |
| 禁止 fire-and-forget | 全仓库没有未等待的事件 Promise |
| ESLint 边界规则 | `core/` 无法 import `plugins/` |

**验收**（对照 [13](./13-PLUGIN-CONTRACT.md) 7.5）：
1. **停用表单插件，系统仍能完整走通销售闭环** → 边界正确
2. 记录实现过程中"接口不够用"的地方 → 写进 [13](./13-PLUGIN-CONTRACT.md) 第 8 节
3. 插件没有碰核心表 → 边界未被破坏

**实现状态（2026-08-18）**：后端原子链路、公开提交限流、编译时静态注册、3 个挂载点、表单管理页和公开页已实现。进入阶段 6 前仍需完成一次真实浏览器角色验收，并确认生产入口会覆盖可信代理 IP 头，否则基于 IP 的限流只能视为应用层辅助保护。

## 5. 每阶段自检

阶段结束时逐条回答：

1. 这个阶段加的东西，**都在范围契约第 3 节里吗**？
2. 有没有"顺手做了"计划外的东西？（有 → 记进变更日志，或删掉）
3. typecheck / lint / test 三个都过了吗？
4. **浏览器实际点过了吗**？
5. 提交了吗？迁移和代码在同一次提交吗？
6. 新建的表加租户隔离测试了吗？

**第 2 条是防止重蹈覆辙的关键。** 上个项目的范围偏移全部来自"顺手做了"。

## 6. 风险与应对

| 风险 | 征兆 | 应对 |
|---|---|---|
| 范围膨胀 | 出现计划外的表/页面/接口 | 走准入规则，或砍掉 |
| 提前优化 | 开始讨论缓存、队列、多套角色读模型 | 回看 [14](./14-TECH-ARCHITECTURE.md) 1.2；轻量固定汇总按容量门槛评审 |
| 迁移事实分叉 | 新旧来源字段同时写、隔离清单久拖不清 | 停止切换；执行 [11](./11-DOMAIN-AND-DATA.md) 4.21.1 的四向核对，禁止长期双写 |
| 容量假设失真 | 仅有文档目标或 1% 计划、没有 100% 证据 | 不宣称百万级；先修查询/索引并复测，消耗返工缓冲 |
| 验证欠账 | 连续两个阶段没跑 typecheck | 停止开发，先补验证 |
| UI 返工循环 | 同一页面反复重做视觉 | 停手，去做 [10](./10-UI-SPEC.md) 第 8 节验收清单 |
| 试用推迟 | "再做一个功能就试用" | 立刻试用，功能后补 |

> **最后一条最危险。** 上个项目"再做一个功能"做了一个月，零真实用户。
